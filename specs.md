# SMART-DORMITORY — Device-based Access (MVP Specs)

## 1. Цель версии

Цель данной версии — реализовать управление IoT-устройствами через единый веб-интерфейс на основе **физического доступа к устройству**, без собственной системы аккаунтов, регистраций и пользовательских профилей.

Дополнительно реализуется **интеграция с Алисой (Yandex Smart Home)** через механизм "Login with Telegram", который выступает мостом между анонимным доступом и требованиями OAuth.

Фокус версии:
- минимализм;
- отсутствие регистрации (email/password);
- использование Telegram как удобного "кошелька" для ключей доступа;
- поддержка голосового управления.

---

## 2. Базовый пользовательский сценарий (MVP)

### Telegram WebApp (Основной)
1. Пользователь открывает SMART-DORMITORY через Telegram WebApp.
2. Система проверяет наличие **закладок (bookmarks)** для данного `telegram_id` в базе данных.
3. Если закладок нет — предлагает ввести код устройства (или сканировать QR).
4. Если код верен:
   - Устройство добавляется в **закладки** пользователя (`telegram_id` <-> `device_id`).
   - Открывается панель управления.
5. При повторном входе устройства подгружаются из закладок автоматически.

### Browser (Локальный)
1. Пользователь открывает сайт.
2. Вводит код устройства.
3. Код сохраняется в `localStorage`.
4. Список устройств формируется на основе локальных данных.
5. Сервер не запоминает пользователя (нет `telegram_id`).

### Алиса (Голосовой)
1. Пользователь в приложении Яндекс выбирает "Добавить устройство".
2. Переходит на страницу авторизации Smart Dormitory.
3. Нажимает кнопку **"Войти через Telegram"**.
4. Система отдает Яндексу список устройств, сохраненных в закладках этого Telegram-аккаунта.
5. Пользователь управляет устройствами голосом.

---

## 3. Концепция доступа (Device-based Access)

**Доступ определяется знанием кода физического устройства.**

В системе отсутствуют:
- Классические аккаунты (User ID, Email, Password).
- Понятие "Владелец" (Owner).
- Права доступа (Admin/Guest) — все равны, у кого есть код.

### Модель "Закладки" (Bookmarks) вместо "Владения"
- Устройство не "принадлежит" пользователю.
- Пользователь просто "сохраняет" ключ к устройству в своем Telegram-кармане.
- Одно устройство может быть сохранено у неограниченного числа пользователей (например, у всех соседей в комнате).

---

## 4. Устройство как единица системы

Сущность `Device`:
- `device_id`: Уникальный ID (напр. mac-адрес или serial).
- `device_secret`: Секретный ключ для авторизации.

Сущность `TelegramBookmark` (Связь):
- `telegram_id`: ID пользователя в Telegram.
- `device_id`: ID устройства.
- `custom_name`: Локальное имя устройства (например, "Моя лампа").
- `room`: Локальное название комнаты (например, "Общага").

---

## 5. Клиентский контекст

### Anonymous Client (Browser)
- Идентификация: НЕТ.
- Хранилище ключей: Browser LocalStorage.
- Взаимодействие с сервером: При каждом запросе передает `device_secret` или временный токен сессии.

### Telegram Client (WebApp)
- Идентификация: `telegram_id` (через `initData`).
- Хранилище ключей: БД сервера (таблица `TelegramBookmark`).
- Преимущество: Ключи не теряются при смене браузера/устройства.

---

## 6. Интеграция с Алисой (Integration Strategy)

Для работы с Yandex Smart Home требуется OAuth 2.0. Поскольку у нас нет логинов/паролей, мы используем паттерн **"Telegram Identity Provider"**.

**Схема работы Bridge:**
1. **Authorize Endpoint:**
   - Пользователь перенаправляется Яндексом на наш URL.
   - Пользователь подтверждает личность через Telegram Login Widget (или WebApp context).
   - Мы получаем подтвержденный `telegram_id`.
   - Генерируем `authorization_code`, привязанный к `telegram_id`.

2. **Token Endpoint:**
   - Яндекс меняет код на `access_token`.
   - `access_token` в нашей базе связан с `telegram_id`.

3. **Discovery & Query:**
   - Яндекс делает запрос "Список устройств" с токеном.
   - Мы находим `telegram_id` по токену.
   - Выбираем из БД все устройства из таблицы `TelegramBookmark` для этого `telegram_id`.
   - Отдаем список Яндексу.

---

## 7. Область ответственности системы

Система отвечает за:
- Валидацию `device_secret` при подключении.
- Хранение закладок пользователей (для удобства и Алисы).
- Синхронизацию статусов (Websocket).
- Реализацию OAuth-провайдера для Яндекса.

Система **НЕ** отвечает за:
- Восстановление доступа при утере `device_secret` (сброс только физически на устройстве).
- Управление конфликтами (если два пользователя шлют разные команды — побеждает последняя).

---

## 8. Ограничения MVP (осознанно)

- Нельзя отозвать доступ у соседа (только смена пароля на устройстве).
- Нет истории действий "кто выключил свет".
- Нет настройки сценариев на сервере.

---

## 9. Техническая реализация (БД)

Мы отказываемся от тяжелой схемы `User` -> `Token` в пользу упрощенной.

### Таблицы (SQLite):
1. **TelegramBookmark**
   - `telegram_id` (BigInteger, Index)
   - `device_id` (String)
   - `device_name` (String, nullable) — для Алисы
   - `room` (String, nullable) — для Алисы
   - *UniqueConstraint(telegram_id, device_id)*

2. **OAuthCode / OAuthToken** (Для Алисы)
   - Стандартные таблицы для хранения токенов, привязанных к `telegram_id`.

---

## 10. Архитектурный принцип

**Device-First.** Устройство первично. Telegram — лишь удобный способ хранить ключи и мост для Алисы.
